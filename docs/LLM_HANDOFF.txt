1. PRODUCT, OWNER, AND SCOPE
---------------------------
Owner/maintainer: Justin. Privately distributed Chrome extension for a small group
of users. Justin handles recipients' initial installation. The product is near
handoff, with an emphasis on preserving working functionality and small changes.

The extension opens a side panel beside the TikTok LIVE product dashboard. It:
- Imports a confirmed opening inventory baseline from Google Sheets.
- Observes rendered auction variations, payment badges, bidding, and Attributed GMV.
- Lets the operator map exact inventory SKUs to variations and queue one next item.
- Tracks reservations, completed sales, inventory, costs, and profit.
- Ends a local session only through the report-producing End flow.
- Saves, manages, corrects, and exports post-stream reports locally.

This is not a TikTok order API integration, a backend service, or a cross-device
inventory system. It does not control the broadcast, bidding, buyer payments, or
TikTok orders. Intended use is one tracker session and one dashboard per computer.

Git/account switching moves source code, NOT the user's Chrome inventory, session,
reports, OAuth authorization, or open dashboard state. Separate Chrome profiles
and separate computers have separate tracker data.

4. EXECUTION, TRUST, AND PERSISTENCE BOUNDARIES
--------------------------------------------
This is plain JavaScript/HTML/CSS, not a React app or a transpiled frontend.
Many modules expose a browser global and CommonJS exports for the Node tests.
Manifest order, importScripts order, and sidepanel/report script order matter.

Flow:
  Rendered dashboard DOM
    -> isolated content script and narrow locators
    -> sanitized, validated runtime event
    -> service worker sender validation and FIFO command processing
    -> canonical coordinator / persistence
    -> best-effort change notification
    -> side-panel read model and rendering

The service worker owns storage and authoritative mutations. Clients should use
existing protocols/coordinators, not read/write Chrome storage directly. Both
chrome.storage.local and chrome.storage.session are restricted to TRUSTED_CONTEXTS.
Storage restriction failures fail closed. UI and content senders have different
allowed commands; do not weaken exact envelope, origin, frame, or sender checks.

Operations are serialized at the worker messageTail and relevant coordinator
operationTail boundaries. Detached candidate state is validated and saved before
successful state is published. Notifications are not the source of truth.
Multiple storage keys are not a single transaction; preserve the explicit repair
paths for partially completed End/payment-resolution operations.

Durable chrome.storage.local keys at this snapshot:
- tiktokLiveTracker.reconciliation: envelope schema 1, inner state version 7.
- tiktokLiveTracker.streamSession: envelope schema 1, inner session version 1.

  Report envelope supports existing legacy schema 1/2 handling and payload v1.

Transient chrome.storage.session keys:

5. DOMAIN AND ACCOUNTING INVARIANTS
---------------------------------
- A local stream ID is local-stream:<UUID>. It is not a verified TikTok room ID.
- Auction identity is (streamId, variationNumber), never variation number alone.
- A stream is pinned to an immutable physical-count inventory baseline lineage.
- Each size has its own exact SKU. UI grouping never merges accounting identities.
- Money is safe integer cents; do not introduce floating-point accounting formulas.
- Payment truth and item mapping are independent axes.
- Canonical paymentStatus is unknown, canceled, or payment_complete.
- Latest observedPaymentStatus is more detailed and may be processing, fixing,
  failed, unrecognized, or not_observed while canonical truth remains unknown.
- Canonical canceled and payment_complete are mutually exclusive terminal results.
  Later contradictory observations do not reverse either automatically. This is
  not a refund or post-completion cancellation system.
- Payment complete requires a successfully parsed positive final sold price before
  capture can create a completed sale. A live bid is never the sold price.
- Every priced completed auction contributes to Gross Item Sales and AOV, even
  unmapped. An unmapped completed sale is an exception, not an absent sale.
- Mapped completed sales drive inventory consumption, COGS, and mapped gross profit.
- Mapping any canonical-unknown variation reserves one unit immediately, including
  bidding, processing, failed/fixing, unrecognized, and price-less completion.
- Canceled releases reservations without sale, revenue, COGS, or profit. The SKU
  link may remain for history. Editing a canceled mapping is reference-only.
- Unmapping a completed sale removes its stock/cost attribution, not its payment
  truth, price, or contribution to Gross Item Sales.
- Mapping/capture may arrive in either order. Repeated events must not double-count.
- Existing completed price conflict handling retains the first accepted price and
  surfaces a conflict instead of silently rewriting final sale truth.
- Oversold inventory remains selectable; report shortages instead of refusing a
  real sale. Displayed stock clamps at zero while oversold counts remain explicit.

Quantities under the pinned baseline:
  remainingQuantity = opening quantity - completed mapped sales
  availableToTagQuantity = remainingQuantity - pending reservations
  displayedAvailableQuantity = max(0, availableToTagQuantity)
  oversoldQuantity = max(0, -availableToTagQuantity)

Fresh physical recounts create new baselines for future streams; historical sales
must not be deducted again from a new opening count. Active append-only imports
derive a new snapshot within the same lineage and preserve already-used rows.

Attributed GMV is the sanitized dashboard display, possibly rounded/compact.
The 6% fee and after-fee figures are presentation estimates, not settled fees or
net profit. Estimated after-fee profit uses GMV * 0.94 minus mapped COGS, rounded
for display. Do not mix these estimates into canonical accounting.

Sold Items detection in sale-candidate-locator.js requires:
- A unique visible root with data-tid="m4b_space".
- Payment elements with data-tid="m4b_tag".
- An exact span label matching /^Variation\s*:\s*#\s*(\d+)$/i.
- A safe row association with exactly one variation label and one payment tag,
  walking no more than 12 ancestors, without using the broad root as a sale row.

Accepted whole badge text, ignoring capitalization and normalized whitespace:
  Payment complete                         -> payment_complete
  Canceled                                 -> canceled
  Cancelled                                -> canceled
  Payment failed                           -> canceled (legacy countdown exception below)
  Payment fixing                           -> payment_fixing
  Payment fixing...                        -> payment_fixing
  Payment fixing…                          -> payment_fixing
  Payment processing                       -> payment_processing
  Payment processing...                    -> payment_processing
  Payment processing…                      -> payment_processing
  Order processing                         -> order_processing
  Order processing...                      -> order_processing
  Order processing…                        -> order_processing

The ellipsis variants above include both three ASCII periods and U+2026.
Outer whitespace is trimmed; whitespace runs collapse. Matching is otherwise exact.
Examples NOT accepted: "Canceled order", "Cancelled order", "Not cancelled",
"Cancelled...", and "Cancelled…". Other nonempty associated badges are
unrecognized; empty badges are skipped. not_observed is a default, not badge text.

8. INVENTORY / GOOGLE SHEETS CONTRACT
-----------------------------------
Sheet tab: Inventory. Only A:F is inventory input. Exact case-sensitive six headers,
each once:
  sku,item,style,size,quantity_on_hand_at_import,unit_cost
Import can accept another column order within A:F; full report exports use the canonical
order. Unknown, missing, or duplicate A:F headers are invalid. A required header in G+
does not count. G+ content, including notes, formulas, and summaries, is ignored for
preview, confirmation, active-stream SKU additions, and quantity-handoff checks.
The first nonblank A:F row is the header. A:F-blank rows are not inventory records,
even if G+ has content; G-only rows neither choose the header nor extend a paste range.

Rows:
- sku: uppercase, unique, regex ^[A-Z0-9][A-Z0-9._-]{0,63}$ after trimming.
- item: required plain text, <=160 characters.
- style: optional plain text, <=160 characters; empty is valid.
- size: required plain text, <=80 characters, own SKU for every size.
- quantity_on_hand_at_import: nonnegative safe integer, actual opening physical stock.
- unit_cost: nonnegative plain USD decimal, no symbol, at most 2 decimal places.
- Zero quantity and zero unit cost are valid. No formulas within A:F; userEnteredValue
  is read so those formulas cannot evade validation by presenting evaluated values.
- Display labels normalize Unicode/whitespace. SKU case/punctuation is not rewritten.
- Duplicate normalized item/style/size identities are invalid, even with unique SKUs.
- Validation is atomic; never partially import a sheet with invalid rows.

Pre-stream Connect and preview -> confirm creates a durable immutable baseline.
Start requires a confirmed baseline; do not reintroduce automatic demo inventory
for ordinary new streams. Legacy recovery is a separate guarded path.

During active tracking, "Add new SKUs from updated Sheet -> Check and add" explicitly
reads the same Sheet's A:F. Every stored field of every existing SKU must remain unchanged;
only new rows may be added. It cannot rename, remove, reprice, or restock existing
stream rows. Existing mappings/counts/baseline lineage must remain consistent.

OAuth/fetch lives in the worker, not content scripts. There is no automatic Sheets
synchronization or write-back. Preview TTL is 10 minutes; request timeout 20 s.
The adapter requests the unbounded-row range 'Inventory'!A:F, then enforces its existing
bounded responses/rows/cells; consult its constants rather than loosening them to work
around invalid Sheets. The existing 1,001-physical-row bound includes the header,
leading A:F blanks, and interior spacers. A:F data beyond it fails closed, not silently
truncated. No new limits were introduced, and G-only rows do not extend used inventory.
This boundary change does not implement formula evaluation, G/H totals, or Apps Script.

Implementation trace: google-sheets-inventory-import.js owns the fixed A:F GET range
for preview, confirmation, append, and readInventoryLayout; the import client/controller
expect the same range metadata. inventory-sheet-import.js::projectInventoryColumns
projects the first six cells before header discovery/validation and trims only trailing
A:F-blank rows. report-quantity-handoff.js::createQuantityHandoff reuses that projection
before layout bounds and positional clipboard construction. Worker/coordinator mutation
ownership, report eligibility, token revalidation, and saved-data contracts are unchanged.

After a report, the operator can copy the complete updated inventory or download CSV.
They back up the Inventory tab, then replace the six-column table starting at A1.
Paste is positional, not a SKU-aware merge. Avoid overwriting newer stock with an old
report. Export quantity excludes completed mapped sales, not merely reservations;
