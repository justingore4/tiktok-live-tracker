1. PRODUCT, OWNER, AND SCOPE
---------------------------
Owner/maintainer: Justin. Privately distributed Chrome extension for a small group
of users. Justin handles recipients' initial installation. The product is near
handoff, with an emphasis on preserving working functionality and small changes.

The extension opens a side panel beside the TikTok LIVE product dashboard. It:
- Imports a confirmed opening inventory baseline from Google Sheets.
- Observes rendered auction variations, payment badges, bidding, and Attributed GMV.
- Lets the operator map exact inventory SKUs to variations and queue one next item.
- Tracks reservations, completed sales, inventory, costs, and profit.
- Ends a local session only through the report-producing End flow.
- Saves, manages, corrects, and exports post-stream reports locally.

This is not a TikTok order API integration, a backend service, or a cross-device
inventory system. It does not control the broadcast, bidding, buyer payments, or
TikTok orders. Intended use is one tracker session and one dashboard per computer.

Git/account switching moves source code, NOT the user's Chrome inventory, session,
reports, OAuth authorization, or open dashboard state. Separate Chrome profiles
and separate computers have separate tracker data.

4. EXECUTION, TRUST, AND PERSISTENCE BOUNDARIES
--------------------------------------------
This is plain JavaScript/HTML/CSS, not a React app or a transpiled frontend.
Many modules expose a browser global and CommonJS exports for the Node tests.
Manifest order, importScripts order, and sidepanel/report script order matter.

Flow:
  Rendered dashboard DOM
    -> isolated content script and narrow locators
    -> sanitized, validated runtime event
    -> service worker sender validation and FIFO command processing
    -> canonical coordinator / persistence
    -> best-effort change notification
    -> side-panel read model and rendering

The service worker owns storage and authoritative mutations. Clients should use
existing protocols/coordinators, not read/write Chrome storage directly. Both
chrome.storage.local and chrome.storage.session are restricted to TRUSTED_CONTEXTS.
Storage restriction failures fail closed. UI and content senders have different
allowed commands; do not weaken exact envelope, origin, frame, or sender checks.

Operations are serialized at the worker messageTail and relevant coordinator
operationTail boundaries. Detached candidate state is validated and saved before
successful state is published. Notifications are not the source of truth.
Multiple storage keys are not a single transaction; preserve the explicit repair
paths for partially completed End/payment-resolution operations.

Durable chrome.storage.local keys at this snapshot:
- tiktokLiveTracker.reconciliation: envelope schema 1, inner state version 7.
- tiktokLiveTracker.streamSession: envelope schema 1, inner session version 1.
- tiktokLiveTracker.streamReports: envelope schema 3, report payload version 2.
  Report envelope supports existing legacy schema 1/2 handling and payload v1.
- tiktokLiveTracker.variationPresets.v1: envelope schema 1, separate per-stream /

Transient chrome.storage.session keys:

These versions differ from protocol versions and manifest version. Never bump one

5. DOMAIN AND ACCOUNTING INVARIANTS
---------------------------------
- A local stream ID is local-stream:<UUID>. It is not a verified TikTok room ID.
- Auction identity is (streamId, variationNumber), never variation number alone.
- A stream is pinned to an immutable physical-count inventory baseline lineage.
- Each size has its own exact SKU. UI grouping never merges accounting identities.
- Money is safe integer cents; do not introduce floating-point accounting formulas.
- Payment truth and item mapping are independent axes.
- Canonical paymentStatus is unknown, canceled, or payment_complete.
- Latest observedPaymentStatus is more detailed and may be processing, fixing,
  failed, unrecognized, or not_observed while canonical truth remains unknown.
- Canonical canceled and payment_complete are mutually exclusive terminal results.
  Later contradictory observations do not reverse either automatically. This is
  not a refund or post-completion cancellation system.
- Payment complete requires a successfully parsed positive final sold price before
  capture can create a completed sale. A live bid is never the sold price.
- Every priced completed auction contributes to Gross Item Sales and AOV, even
  unmapped. An unmapped completed sale is an exception, not an absent sale.
- Mapped completed sales drive inventory consumption, COGS, and mapped gross profit.
- Mapping any canonical-unknown variation reserves one unit immediately, including
  bidding, processing, failed/fixing, unrecognized, and price-less completion.
- Canceled releases reservations without sale, revenue, COGS, or profit. The SKU
  link may remain for history. Editing a canceled mapping is reference-only.
- Unmapping a completed sale removes its stock/cost attribution, not its payment
  truth, price, or contribution to Gross Item Sales.
- Mapping/capture may arrive in either order. Repeated events must not double-count.
- Existing completed price conflict handling retains the first accepted price and
  surfaces a conflict instead of silently rewriting final sale truth.
- Oversold inventory remains selectable; report shortages instead of refusing a
  real sale. Displayed stock clamps at zero while oversold counts remain explicit.

Quantities under the pinned baseline:
  remainingQuantity = opening quantity - completed mapped sales
  availableToTagQuantity = remainingQuantity - pending reservations
  displayedAvailableQuantity = max(0, availableToTagQuantity)
  oversoldQuantity = max(0, -availableToTagQuantity)

Fresh physical recounts create new baselines for future streams; historical sales
must not be deducted again from a new opening count. Active append-only imports
derive a new snapshot within the same lineage and preserve already-used rows.

Attributed GMV is the sanitized dashboard display, possibly rounded/compact.
The 6% fee and after-fee figures are presentation estimates, not settled fees or
net profit. Estimated after-fee profit uses GMV * 0.94 minus mapped COGS, rounded
for display. Do not mix these estimates into canonical accounting.

Sold Items detection in sale-candidate-locator.js requires:
- A unique visible root with data-tid="m4b_space".
- Payment elements with data-tid="m4b_tag".
- An exact span label matching /^Variation\s*:\s*#\s*(\d+)$/i.
- A safe row association with exactly one variation label and one payment tag,
  walking no more than 12 ancestors, without using the broad root as a sale row.
- Ambiguous roots, rows, duplicate variation candidates, and unsafe associations

Accepted whole badge text, ignoring capitalization and normalized whitespace:
  Payment complete                         -> payment_complete
  Canceled                                 -> canceled
  Cancelled                                -> canceled
  Payment failed                           -> canceled (legacy countdown exception below)
  Payment fixing                           -> payment_fixing
  Payment fixing...                        -> payment_fixing
  Payment fixing…                          -> payment_fixing
  Payment processing                       -> payment_processing
  Payment processing...                    -> payment_processing
  Payment processing…                      -> payment_processing
  Order processing                         -> order_processing
  Order processing...                      -> order_processing
  Order processing…                        -> order_processing

The ellipsis variants above include both three ASCII periods and U+2026.
Outer whitespace is trimmed; whitespace runs collapse. Matching is otherwise exact.
Examples NOT accepted: "Canceled order", "Cancelled order", "Not cancelled",
"Cancelled...", and "Cancelled…". Other nonempty associated badges are
unrecognized; empty badges are skipped. not_observed is a default, not badge text.

7. CAPTURE DELIVERY AND HEALTH
------------------------------
Capture implementation:
- Scoped MutationObservers handle Sold Items, GMV, and active auction/bid probes.
- Lifecycle rediscovery runs every 250 ms and on relevant SPA/navigation events.
  Rediscovery is not a guarantee that virtualized historical rows are rendered.
- Sold Items/GMV scans use 150 ms quiet delay and 1,000 ms maximum wait.
- Bidding scans use 75 ms quiet delay and 250 ms maximum wait.
- Delivery order is variation observations, payment statuses, then completed sales.
- Failed delivery retries back off 1, 2, 4, then 5 seconds, capped at 5 seconds.
- Acknowledgment follows persistence. Stale failed retries must not overwrite newer
  observed statuses. Diagnostic event deduplication is not durable reconciliation.
- Body/route changes invalidate stale delivery context. Same-body scoped root
  replacement preserves appropriate delivery state for recovery.
- GMV uses exact guide-Step-2 and supported legacy guide-step-2 roots; active auction
  uses a unique visible .auction-pin-card. See locator tests before editing selectors.

Startup-readiness presentation (existing capture-health filenames, protocol v2):
  connecting  Blue    Connecting
  loading     Yellow  Loading
  active      Green   Capture active
  blank       Neutral Reload Site; accessible static disclaimer, no focus target
  not_tracking is internal/hidden with no reserved row.

8. INVENTORY / GOOGLE SHEETS CONTRACT
-----------------------------------
Sheet tab: Inventory. Exact case-sensitive six headers, each once:
  sku,item,style,size,quantity_on_hand_at_import,unit_cost
Import can accept another column order; full report exports use the canonical order.
Extra, missing, or duplicate headers are invalid. Blank rows are ignored.

Rows:
- sku: uppercase, unique, regex ^[A-Z0-9][A-Z0-9._-]{0,63}$ after trimming.
- item: required plain text, <=160 characters.
- style: optional plain text, <=160 characters; empty is valid.
- size: required plain text, <=80 characters, own SKU for every size.
- quantity_on_hand_at_import: nonnegative safe integer, actual opening physical stock.
- unit_cost: nonnegative plain USD decimal, no symbol, at most 2 decimal places.
- Zero quantity and zero unit cost are valid. No formulas; userEnteredValue is read
  so formulas cannot evade validation by presenting evaluated values.
- Display labels normalize Unicode/whitespace. SKU case/punctuation is not rewritten.
- Duplicate normalized item/style/size identities are invalid, even with unique SKUs.
- Validation is atomic; never partially import a sheet with invalid rows.

Pre-stream Connect and preview -> confirm creates a durable immutable baseline.
Start requires a confirmed baseline; do not reintroduce automatic demo inventory
for ordinary new streams. Legacy recovery is a separate guarded path.

During active tracking, "Add new SKUs from updated Sheet -> Check and add" explicitly
reads the same Sheet. Every stored field of every existing SKU must remain unchanged;
only new rows may be added. It cannot rename, remove, reprice, or restock existing
stream rows. Existing mappings/counts/baseline lineage must remain consistent.

OAuth/fetch lives in the worker, not content scripts. There is no automatic Sheets
synchronization or write-back. Preview TTL is 10 minutes; request timeout 20 s.
The adapter has bounded responses/rows/cells; consult its constants rather than
loosening them to work around invalid Sheets. One header plus up to 1,000 inventory
rows is the intended bounded grid use.

After a report, the operator can copy the complete updated inventory or download CSV.
They back up the Inventory tab, then replace the six-column table starting at A1.
Paste is positional, not a SKU-aware merge. Avoid overwriting newer stock with an old
report. Export quantity excludes completed mapped sales, not merely reservations;
oversold replacement quantity clamps to zero and needs a physical recount.

9. TRACKER CONTROLS AND UI DECISIONS TO PRESERVE
---------------------------------------------
- Cards group normalized item+style; sizes select exact SKUs. Single-row groups map
  directly. Search covers SKU/item/style/size. Filtering, ordering, and counts are
  existing view-model behavior, not quantities guessed from card labels.
- Left-click selects/unmaps for the viewed variation.
- On live: right-click maps if unassigned; if already mapped, toggles next-item queue.
- In history: right-click targets live/newest without changing history selection or
  the queue. Preserve the explicit distinct workflow.
- Queue holds one SKU for the next genuinely newer bidding variation and does not
  replace existing mapping. It is not a multi-item backlog.
- The red inventory-header badge shows the queued item/style and size (OS/n/a
  omitted). Its X uses clearQueue, never toggleQueue or mapping commands.
- getQueueSnapshot returns an ephemeral queueToken alongside queuedSku. Clear
  checks that token, stream, and SKU inside the serialized coordinator; stale
  requests are rejected. Tokens rotate on queue writes and worker restarts and
  are not persisted. Queue storage remains schema 1.
- Return to live item resumes follow-newest. Pins move cards to front; otherwise
  preserve original order. Completed sales do not cause reordering.
- Size/variation pickers use dedicated render locking so updates do not jump under
  the pointer. Latest queued render applies on release; this is not the health lock.

Current compact visual decisions:
- Preset items occupies the right slot of the existing startup badge row. Enter
  a total 1–1000 (#1–#N, not N additional), then Reset presets replaces the field.
  Totals below the highest actual capture are rejected; real capture is not capped.
  Clicking outside an unsaved total field discards its draft and restores the
  bubble without saving or moving focus. Inside clicks keep editing; an accepted
  in-flight save retains its context. Enter saves and Escape still cancels.
  Var # also finds preset placeholders. Future selection is display-only history
  browsing. With no captured variations or selected preset, opening the dropdown
  highlights/scrolls #1 without committing it. Existing selections and explicit
  Home/End boundaries retain priority; the descending option order stays unchanged.
  A successful initial create before capture also directly selects future #1.
  This is a one-shot submit action, never a refresh/reopen or range-extension rule.
  One canonical verification read waits behind any own-notification refresh; stale
  captures, navigation, controller/session or preset identity changes suppress the
  automatic selection. A validated capture-notification generation also protects
  against captures whose debounced panel refresh has not arrived yet. No canonical
  order or reservation is created by selecting #1. Return to live stays hidden until
  there is an actual captured variation, then uses normal future/history visibility.
  Left-click plans/unplans an SKU. Right-click fills an empty current
  future preset and stays, or saves the next higher empty uncaptured preset and
  opens it. Skip assigned/captured entries; never wrap or replace an assignment.
  Exhaustion announces "No more future variations." without changing anything.
  Live and captured historical right-clicks keep their existing behavior.
  Untracked plans do not reserve stock or affect reports/metrics/exports.
- Pre-stream planning: after confirmed inventory and local Start/Resume, presets
  work with zero captured variations once existing Connecting/Loading ends. The

11. REPORT LIBRARY, CAPACITY, AND CORRECTIONS
------------------------------------------
Exact limits in shared/stream-report-storage.js:
- MAX_ACTIVE_REPORTS = 5 recent finalized records.
- MAX_ARCHIVED_REPORTS = 25 archived finalized records.
- MAX_TOTAL_REPORTS = 30, including hidden pending records.
- MAX_ARCHIVE_BYTES = 4,202,496 bytes.
  That is 4 MiB + 4 KiB legacy-migration headroom + 4 KiB display-name headroom.
  Do NOT replace it with a hardcoded bare 4 MiB or total Chrome storage usage.
- Report envelope schema 3; payload version 2. Display-name maximum 80 characters.

Byte size is UTF-8 JSON for the complete {schemaVersion, records} envelope, including
current, archived, pending records and overhead. Warning and enforcement share the
measurement path. Capacity reads are validated/read-only; no client storage access,
silent migration/repair on capacity read, or serialization on every UI render.
Relevant symbols: storage.measureRecordsByteLength / requireSafeEnvelopeSize,
coordinator.getLibraryCapacity, and sidepanel.js::renderReportCapacityWarning.

When a sixth recent report is finalized, the oldest finalized recent record can
move to archive if room exists. No automatic deletion/pruning. Restore requires
available recent slots; it does not automatically evict a different recent report.

Capacity warning beside View archived reports, before starting:
- <=3 total slots remaining: existing red slot warning, singular/plural preserved.
- >=80% and <90% byte usage: yellow storage warning.
- >=90% and <100%: red storage warning.
- Both conditions: combined red slot/storage bubble.
- Zero slots or reached byte ceiling: "Report library full - delete an archived report"
  (display typography may use an em dash).
- Decisions use unrounded ratio; displayed percent floors so it cannot show 100%
  before the actual ceiling. Missing/invalid/failed capacity is not zero usage.
- Stale async responses cannot overwrite newer state; refresh through library flows.
- No new Start-blocking rule from this advisory bubble. Even below 80%, one large
  report could exceed remaining bytes; the warning is not a next-report guarantee.
- Tooltip explains downloading wanted reports then deleting unneeded ones;
  archiving alone does not free bytes or total slots.

Management:
- Recent report menu: Download PDF, Rename, Archive, Delete.
- Recent Delete uses the same explicit permanent-delete confirmation as archives;
  it does not require archiving first. Cancel preserves the record.
- Archived reports support restore, selection/bulk actions, and permanent deletion.
- Default report name uses tracking START time. Preserve edited names and tier.
- No silent data deletion to make space. Library management is hidden while tracking.

Three correction workflows, NOT interchangeable:
1. Finish unresolved payments
   - Newest eligible finalized report, no active session, compatible baseline and
     latest canonical stream. Completion requires seller-verified final price.
   - Saves canonical payment/inventory change first, then regenerates the report.
2. Correct Item Mapping
   - Report-only, completed/canceled saved variations under existing eligibility
   rules (no active stream, no active-bidding marker at End, and no blocking
   unresolved/pending conditions).
   - Changes selected report/export only; canceled mappings remain reference-only.
3. Correct SKU Unit Cost
   - Any eligible finalized current/archived report, including unsold SKUs and zero.
   - Changes that report's costs, metrics, profit and inventory export only.
   - NOT canonical inventory, other reports, or future streams. "Permanent" means
     persistent within that report until deliberately corrected again.

Saved-cost preservation FIX ALREADY IMPLEMENTED:
Previously, completing/canceling an unfinished payment rebuilt from canonical
inventory and could erase saved report-only cost corrections.
